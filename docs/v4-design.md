## 1. `apt-core` — 경계 · 노트북 일치 테스트 · 지역 / 주택 유형 인자

목표: 노트북에서 검증한 계산을 **한 줄도 바꾸지 않고** 패키지로 옮겨, 학습(전체 거래)과 서빙(단지 · 면적 · 층 질의 1건)이 **같은 함수**를 쓰게 한다. 옮긴 결과가 노트북 산출물과 같은지 테스트로 증명하기 전에는 파이프라인 · API를 만들지 않는다.

### 1-3. 경계 원칙

| 원칙 | 내용 | 이유 |
|---|---|---|
| 순수 함수 | `apt-core`는 DataFrame + 기준일을 받아 DataFrame을 돌려준다. 네트워크 · 파일 쓰기 · 환경변수 읽기 없음 | 일치 테스트가 네트워크 없이 돌고, 같은 함수를 CronJob(전체)과 API(1건)가 함께 쓴다 |
| 수집은 밖에서 | API 호출 · 원본 저장은 `pipeline/collect/`(0Xa~e 스크립트 이식), 서빙 DB 쓰기는 `pipeline` | 수집 실패 · 재시도 · 멱등성은 2장에서 따로 설계 |
| 시점 규칙은 데이터 | 출처마다 `사용가능일` 열 → 기준일 이전 행만 as-of 결합 (`point_in_time.py`) | 06의 시점 규칙을 학습 · 서빙이 똑같이 지킨다 |
| 질의 경로 = 거래 경로 | 서빙 질의(단지 · 전용면적 · 층 · 기준일)는 `거래유형=중개거래`, `계약일 = 기준일`(매달 1일 · 매주 금요일, 2-1)인 **가상 거래 1행**으로 만들어 같은 Feature 함수에 넣는다 (`model_config.json`의 `service_input`) | 학습 · 서빙 불일치를 구조로 막는다 |
| 노트북은 기록 | 노트북은 고치지 않는다. 바뀐 계산은 `apt-core`에서만 하고 테스트 기준값을 같이 바꾼다 | V2 · V3 결과의 재현성 유지 |

### 1-4. 노트북 일치 테스트

기준값은 **커밋된 노트북 산출물**이다 (`data/v2_5year_seoul/processed/` 50개 파일 · `models/regression/v2/` 7개 파일이 Git에 있음, 팩 317MiB).

| # | 테스트 | 비교 | 통과 기준 |
|---|---|---|---|
| T1 | 모듈별 Feature | 각 모듈 출력 ↔ 노트북 중간 parquet (`market_leading_v2` · `school_environment_v2` · `policy_trade_v2` · `complex_trade_v2` 등) | 키 1:1, 정수 · 문자열 **완전 일치**, 실수 **완전 일치 목표** — 다르면 원인(연산 순서 등)을 찾아 기록한 뒤에만 상대 오차 1e-12 허용 |
| T2 | 최종 거래 표 | `merge` 출력 ↔ `v2_trade.parquet` 234,302행 × Feature 201열 | T1과 같음 + 행 수 · 키 · 열 순서 · dtype 같음 |
| T3 | 질의 경로 | Test 기간 중개거래를 (단지 · 면적 · 층 · 계약일) 질의로 다시 만든 행 ↔ `v2_trade` 같은 행 | 201열 일치 (계약일을 질의 기준일로 넣었을 때) |
| T4 | 추론 | 저장 모델 `lgbm_regression_v2.txt.gz`로 `apt-core` 예측 ↔ 노트북 방식 예측 | 완전 일치 (같은 트리 · 같은 입력) |
| T5 | 재학습 재현 | 같은 데이터 · 설정으로 다시 학습한 모델 ↔ 저장 모델 | **1-5 실측으로 기준 결정** |
| T6 | 범위 · 등급 | `interval.py`의 2026-08 범위표 ↔ `interval_table.csv`, 흐름 구간 추가 규칙 ↔ `r11_interval5.csv` (Valid 80.5% · Test 81.3%) | 분위수 완전 일치, 포함률 소수 둘째 자리까지 같음 |
| T7 | 시점 누출 (06 검사 이식) | 기준일 이후 자료를 지우고 다시 계산해도 같은 값, 시차를 1개월 줄이면 실패해야 함(시험의 시험) | 06과 같음 |
| T8 | 레지스트리 계약 | 출력 열 = 레지스트리 `role == model` 201개, 금지 열(정답 · 거래 이후 정보) 없음 | 완전 일치 |
| T9 | 지역 흐름 · 태그 | `region_flow.py` ↔ `gu_trend_weekly.parquet`, `tags.py` ↔ `complex_tags.parquet` | 완전 일치 |

**CI 실행 환경:** 저장소가 공개라 GitHub 호스트 러너가 Linux x64 · **arm64 모두 4 CPU · 16GB RAM · 14GB SSD** ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), 2026-11-18 조회). 로컬 재학습 최대 2.4GiB(Phase 4-4 측정)라 전체 데이터로 T1~T9를 CI에서 돌릴 수 있다 → **x64 · arm64 두 러너에서 실행**(배포 VM이 ARM).

**CI로 못 하는 부분:** 원본이 gitignore된 단계 — 상가정보 원본(서울 CSV 25개, 약 6.9GB) → 학원 추출, 공시가격 호 단위 원본(약 63MB) → 단지 집계, 건축물대장 원본 → 공동주택 추출. 이 단계는 CI에서 **커밋된 중간 산출물부터** 테스트하고, 원본 → 중간 단계는 로컬에서 한 번 일치를 확인해 결과를 기록한다.

### 1-5. 재학습 재현성 (T5 기준, 실측)

LightGBM 공식 문서: `deterministic=true`는 같은 데이터 · 같은 설정에서 결과를 안정시키지만, **다른 시드 · 다른 LightGBM 버전 · 다른 컴파일러 · 다른 시스템에서는 결과가 다를 수 있다**고 명시하고, 수치 불안정을 피하려면 `force_col_wise` 또는 `force_row_wise`를 함께 켜라고 한다 ([Parameters](https://lightgbm.readthedocs.io/en/latest/Parameters.html#deterministic)). 현재 저장 모델은 `deterministic`을 켜지 않았다 (`model_config.json`).

**실측 (2026-11-18, 로컬 Windows x64 · 같은 venv, `v2_trade` 234,302행, 트리 2,080개):**

| 조건 | 학습 시간 | 트리 텍스트 | 예측 차이 (log, 최대) |
|---|---:|---|---:|
| 저장 모델과 같은 설정 (`n_jobs=8`) | 91초 | **완전히 같음** | 0 |
| 스레드만 바꿈 (`n_jobs=2`) | 135초 | 다름 | 3.6 × 10⁻¹⁵ (가격 차이 0.0000%) |

→ 같은 플랫폼 · 같은 설정이면 `deterministic` 없이도 저장 모델이 그대로 다시 나온다. 스레드 수만 바뀌어도 트리 텍스트는 달라지지만 차이는 부동소수점 반올림 수준이다.

**T5 기준 (결과 전에 고정):**
1. x64 CI · `n_jobs=8`: 트리 텍스트 **완전 일치** (이식이 맞다는 증명은 이것으로 한다)
2. 스레드 수가 다를 때: 전체 행 예측 최대 |Δlog| ≤ 1e-9 (10억 원 집에서 약 1원)
3. arm64 CI: 같은 기준 2로 확인. 넘으면 기준을 늘리지 않고 차이 크기를 기록한 뒤, 매달 재학습 결과는 이 테스트 대신 **2-6 게이트(전 달 대비 적정가 변화)와 7-3 OOF 감시(MAPE · 범위 포함률)**로 검증한다 — 공식 문서상 시스템이 다르면 같은 결과를 보장하지 않으므로
- `deterministic=true`는 켜지 않는다: 저장 모델을 그대로 재현하는 것이 확인됐고, 켜면 모델이 바뀌어 V2 · V3 결과와 비교가 끊긴다

### 1-6. 지역 · 주택 유형 인자 (V5 · V6 대비)

- `Scope(region: 시도 코드 목록, housing_type)` — V4는 `Scope(region=["11"], housing_type="apartment")` 하나. 수집 · Feature · 모델 산출물 경로와 서빙 DB 키에 둘 다 들어간다
- **출처마다 지원 지역을 선언**하고, 지원하지 않는 지역으로 실행하면 결측으로 채우지 않고 **시작 시 실패**시킨다 — V5에서 조용히 Feature가 비는 것을 막는다
- V4에서 열 이름(`서울_확정월_중위가격` 등)은 바꾸지 않는다: 이름을 바꾸면 저장 모델 · 일치 테스트가 깨진다. 계산 함수만 `시도` 단위로 일반화하고 이름은 설정에서 붙인다 (V5 재학습 때 `시도_*`로 변경)
- V5에서 바꿔야 할 서울 전용 출처 (1-2 표): 정책 이벤트 · 토허 단지 범위, 서울 정비사업 추진현황, 서울 T-Data 역 출입구, 서울 상권분석 직장인구, EDSS 서울 필터 → V5 시작 시 전국 대체 출처를 조사한다
- 주택 유형: 국토부 실거래 API가 유형마다 다르고(아파트 · 연립다세대 · 오피스텔 · 단독다가구), `06_last_trade`처럼 **단지 · 같은 면적 반복 거래**를 전제한 Feature는 빌라 · 단독에서 거의 생기지 않는다 → V6은 수집기 추가만이 아니라 Feature를 다시 설계해야 한다. `apt-core`는 유형별 Feature 묶음 목록을 설정으로 받는다

### 1-7. 패키지 · 의존성 · 순서 · 완료 기준

- **위치:** `packages/apt-core/` (`pyproject.toml`, `pip install -e`), 노트북 · `data/` · `models/`는 옮기지 않음 (3장)

## 2. 파이프라인 — 일정 · 멱등 키 · 실패 처리 · 품질 게이트

### 2-1. 핵심 사실: 재학습은 한 달에 한 번, 예측은 매주 (2026-11-25 변경)

- 서비스 질의는 `계약일 = 기준일`인 가상 거래다 (1-3, 기준일 = 매달 1일 재학습 · 매주 금요일 재예측). 월 단위 자료는 그 달 안에서 고정되고, 같은 면적 직전 거래 · 시세 보정 · 예상가격만 기준일마다 바뀐다: 실거래 · 부동산원 월간은 m-2월, 직전 거래는 계약일 30일 전까지, 시세 보정 지수는 계약일 전 공표분, 정책 · 역은 계약일 이전분
- 11의 서비스 방식 평가도 같다: **m월 예측 = m월 1일에 확정된 거래(m-2월까지)로 학습한 모델** (11 5장, 54개월 OOF)
- → **재학습 · 범위표는 매달 1일 한 번**, **적정가 예측은 매주 금요일 다시** 한다 (아래 백테스트로 2026-11-25 변경). 주간 재예측은 이번 달 모델을 그대로 쓰고 질의일만 그 금요일로 바꿔 같은 면적 직전 거래 · 시세 보정 · 예상가격을 다시 계산한다. 시장 · 금리 · 정책 등 월 단위 Feature는 그 달 값 그대로다. 달 중간에 발표된 정책은 다음 달 재학습에 반영된다 (화면에 기준일 표시, 기획서 6장 S3)

**주간 재예측 백테스트 (기준은 결과 전 고정, 2026-11-25)**

- 질문: 재학습은 매달 1일 그대로 두고, **예측만 매주 다시** 하면(새로 신고된 같은 면적 직전 거래 · 새 주간 지수 반영) 오차가 줄어드나?
- 기간: **Valid 2025-07 ~ 12** (Test는 선택에 쓰지 않는다). 각 월 m은 m-2월까지 확정된 거래로 학습한 모델 하나(설정 = `model_config.json`)로 세 가지 입력을 예측해 비교한다
  - 월간(현재 설계): 질의일 = m월 1일 기준의 직전 거래 · 시세 보정 · 예상가격
  - 주간: 질의일 = 계약일 이전 마지막 금요일(지수 목요일 공표 다음 날), 단 m월 1일보다 앞이면 m월 1일
  - 매일(상한 참고): 질의일 = 계약일 (지금 학습 행 그대로)
- 평가: 중개거래 MAPE, 서비스가 판정하는 거래(기존 단지 · 월간 기준 직전 거래 1년 이내)와 전체를 함께 본다

**결과 (2026-11-25):** 재현 확인 — 질의일 = 계약일로 다시 계산한 Feature 8개가 학습 행과 100% 같고, 매일 입력 예측은 저장된 OOF와 차이 0.

### 2-3. 실거래 재수집 범위 · 호출량 (실측)

**해제는 계약 후 늦게 붙는다.** 2021-07 ~ 2026-06 원본 247,385건 중 해제 13,083건(5.29%)의 `해제사유발생일 − 계약일`:

| 지연 | 50% | 75% | 90% | 95% | 99% | 최대 |
|---|---:|---:|---:|---:|---:|---:|
| 일 | 33 | 70 | 108 | 145 | 322 | 1,122 |

누적: 30일 이내 48.1% · 90일 84.7% · 180일 96.8% · **365일 99.3%**

- → 매일 **최근 13개월**(계약월 기준)을 다시 받는다: 해제의 99.3%를 잡는다. 13개월보다 오래된 해제(0.7%)는 `monthly`에서 직전 5년 전체를 한 번 더 받아 반영한다
- 호출량: 서울 25개 구 × 13개월 = 325 묶음. 구 × 월 거래 수는 중앙값 123건 · 최대 1,039건이라 묶음당 1~2쪽 → **하루 최대 약 650회 × 2종(매매 · 전월세)**. 공공데이터포털 개발계정 트래픽은 API마다 **일 10,000건** ([15126468 상세](https://www.data.go.kr/data/15126468/openapi.do), 2026-11-18 조회) → 매매 기준 6.5%
- 월간 전체 재수집(60개월 × 25구 ≈ 1,500묶음, 최대 약 3,000회)도 한도 안. 넘으면 기존 스크립트처럼 체크포인트로 다음 날 이어 받는다

- **설계:**
  1. **멱등 단위 = (시군구, 계약월) 묶음.** 수집할 때마다 그 묶음을 API 응답 전체로 **통째로 교체**한다 (한 트랜잭션). 몇 번을 다시 돌려도 결과가 같다 — CronJob이 두 번 실행되거나 건너뛸 수 있다는 공식 문서 조건을 만족 ([CronJob](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/))
  2. 행 키 = `해시(나중에 바뀌지 않는 열) + 같은 해시 안 순번`. 나중에 바뀌는 열(`해제여부` · `해제사유발생일` · `등기일자`)은 해시에서 뺀다. 완전히 같은 거래는 서로 바꿔도 결과가 같아 순번으로 충분하다
  3. 키마다 **처음 본 날짜(`first_seen`)**를 기록한다 → V2 한계("2026년에 받은 자료라 그 사이 해제된 거래가 빠짐")를 앞으로는 없애고, 실제 신고 지연 분포를 재서 m-2 규칙을 다시 검토할 근거가 된다
- 다른 출처도 같은 원칙: 월 · 주 · 연 단위 묶음을 통째로 교체, 스냅샷은 수집일을 키로 추가만

### 2-5. `monthly` 순서와 모델 버전

m월 1일 실행 (예: 2026-12-01 → 확정월 2026-10):

1. 오늘 `collect-daily`가 성공했는지 확인 (실패면 수집부터 다시)
2. 월간 출처 수집 (부동산원 월간 · ECOS · KOSIS · 통계누리 미분양 · 인허가 · 청약홈)
3. **OOF 추가:** 새로 확정된 m-2월 거래를 **m-2월에 서빙했던 모델**로 예측해 `r = log(실제/예측)` 저장 → 범위표(m-4 ~ m-2월 잔차)와 단지 최근 잔차(계약일 [d−395, d−30])의 입력. 그래서 **모델 버전은 최소 3개월 보관**한다 (11 OOF와 같은 정의)
4. 범위표 m월 (단지 × 가격대 × 단지 최근 흐름, 0.08 / 0.92 분위수, 3개월 창)
5. 재학습: m-2월까지 확정 거래, 설정 · 반복 2,080회 고정 (`model_config.json`). 측정 91 ~ 135초 (1-5)
6. 일괄 추론: 서빙 대상(단지 × 전용면적, 3장에서 확정)의 m월 적정가 · 범위
7. 게이트 (2-6) → 통과하면 **새 버전 `YYYY-MM`으로 서빙 테이블에 쓰고, 마지막에 "현재 버전" 표시 하나만 바꾼다** (한 트랜잭션). 실패하면 전 달 버전을 그대로 서빙하고 화면에 모델 기준일이 전 달로 보인다
- 같은 달 다시 실행해도 같은 버전을 덮어쓴다. 같은 플랫폼 · 설정이면 학습 결과가 같다 (1-5 실측)
- Job 설정: `backoffLimit: 2`, `activeDeadlineSeconds`는 ⑤ k3d에서 전체 실행 시간을 잰 뒤 3배로 정한다

### 2-6. 품질 게이트 (결과를 보기 전에 고정)

| 단계 | 검사 | 실패 시 |
|---|---|---|
| 실거래 묶음 | 열 이름 · 형식이 기대와 같음 | 그 묶음 교체 안 함 (직전 데이터 유지) |
| 실거래 묶음 | 행 수가 직전 수집보다 줄지 않음 — 해제는 행이 지워지지 않고 `해제여부 = O`로 남는다(원본에 해제 13,083행이 있음) | 교체 안 함. **3일 연속** 같으면 실제 삭제(정정)로 보고 교체 + 경고 |
| Feature (m월) | 열별 결측률 ≤ max(학습 기간 결측률 × 2, 학습 기간 + 5%p) (레지스트리 `na_rate`), 학습 기간 상수였던 열 제외 | 공개 중단, 전 달 유지 |
| 재학습 | 트리 2,080개 완료, 예측에 NaN · 무한대 없음 | 공개 중단 |
| 일괄 추론 | 같은 대상의 전 달 대비 적정가 변화 중앙값이 과거 최대치 이하 | 공개 중단. 기준값은 ① 단계에서 직전 12개월 매달 재학습을 다시 돌려 월간 변화 분포를 재고 그 최댓값으로 고정 (**추정 → 실측 예정**) |
| 감시 (공개는 막지 않음) | 새로 확정된 m-2월 중개 OOF MAPE > **6.4%** | 경고만. 오래된 모델로 되돌려도 시장 변화는 못 고치므로 자동 되돌림 없음 |

- 6.4% 근거: 최근 24개월(2024-07 ~ 2026-06) 월별 중개 OOF MAPE 평균 4.79% · 표준편차 0.53 · 최대 5.64% → 평균 + 3σ (`oof_predictions.parquet`, 2026-11-18 측정). 54개월 전체 최대 14.24%는 거래가 적던 2022년 초라 기준에서 뺐다
- 80% 범위 실제 포함률 · Feature 드리프트 · 학습 범위 밖 값 감시와 설정 변경(섀도 운영) 규칙은 7장
- 모든 실행은 `pipeline_runs` 테이블에 기록: 작업 · 묶음/버전 · 시작/끝 · 상태 · 행 수 · 검사 결과(JSON). 이 표가 멱등 확인과 운영 화면(2차 Admin)의 원천이다

### 2-7. 못 막는 것 (한계)

- 2월이 낀 달은 신고 기한이 m월 1일보다 1~2일 늦게 끝날 수 있다 (06 한계 그대로) → `first_seen`이 쌓이면 실제 누락 비율을 재서 판단
- 공시가격 · 학교 통계처럼 수동인 연간 자료가 늦으면 그 Feature는 전년 값으로 계산된다 (시점 규칙상 정상). 운영 달력에 마감일을 둔다: 공시가격은 6월 중, 학교는 공시 후
- 서울 전용 출처(1-6)는 V5에서 바뀐다. 수집기는 `Scope`를 받아 지원하지 않는 지역이면 시작 시 실패한다

## 3. 서빙 데이터 · API

### 3-1. 결정: 적정가는 전부 미리 계산하고, API는 읽기만 한다 (실측)

적정가가 한 주에 한 번 바뀌므로(2-1), 화면에서 고를 수 있는 모든 (단지 × 전용면적 × 층)을 `monthly` · `predict-weekly`에서 미리 계산한다.

| 측정 (2026-11-18, 로컬 8코어 x64) | 값 |
|---|---|
| 5년간 거래된 단지 · (단지, 전용면적) | 7,871 · **23,172** (최근 1년만 보면 15,611) |
| 단지당 전용면적 수 중앙값 | 2 |
| 1 ~ 최고층까지 모든 층을 펼친 행 | **360,325** (최고층 중앙 12 · 최대 69, 최고층 결측 92개 단지는 거래된 최고층으로 대체) |
| 360,325행 일괄 예측 (LightGBM, 저장 모델) | 2스레드 75초 · 4스레드 59초 |
| 요청 1건 예측 (참고: 요청 시 추론을 했을 경우) | 1행 p50 2.2ms · p95 4.9ms, 40행(모든 층) p50 15ms |

- → **`analysis-service`는 LightGBM을 싣지 않는다.** 모델은 파이프라인에만 있고, API는 Postgres 기본 키 조회만 한다. 그래서 화면 · 호가 판정 · AI 상담이 **같은 표의 같은 숫자**를 보여 준다 (12장 "숫자는 ML")
- 화면의 전용면적 선택지는 **5년간 거래된 면적만** 보여 준다. 거래가 없던 면적은 같은 면적 직전 거래 Feature가 없고 범위도 참고용이라 1차에서 제공하지 않는다
- 전용면적은 원값(예: 84.97 · 84.99)을 그대로 쓴다. 모델 입력이 원값이고, 1㎡ 반올림으로 묶으면 23,172 → 18,798개로 줄지만 서로 다른 평형이 섞인다
- Feature 계산 시간(36만 질의 행)은 아직 모른다 → ① 단계에서 재고, 길면 같은 단지 · 면적에서 층만 다른 행은 Feature를 한 번 만들고 `층`만 바꾸는 방식으로 줄인다 (층에 따라 바뀌는 Feature가 `층`뿐인지 그때 레지스트리로 확인)

### 3-2. 서빙 테이블 (Postgres `serving` 스키마, 쓰기 = 파이프라인 · 읽기 = API)

| 테이블 | 키 | 주요 열 | 갱신 |
|---|---|---|---|
| `model_version` | `version`(YYYY-MM) | 학습 확정월, 학습 거래 수, 게이트 결과, 공개 시각, OOF MAPE(감시) | 매달 |
| `serving_current` | (1행) | 현재 공개 `version` | 매달 마지막 한 번 (2-5) |
| `complex` | `complex_id`(국토부 단지일련번호) | 단지명 · 주소(지번 · 도로명) · 좌표 · 구 · 세대수 · 준공연도 · 태그 · 신규 단지 여부 | 매달 |
| `fair_price` | (`version`, `기준일`, `complex_id`, `area_m2`, `floor`) | 적정가(만원) · 범위 하한 · 상한(만원) · 범위 구간(단지 × 가격대 × 흐름) · **판정 가능 여부 + 참고용 사유** · **설명 근거**(같은 면적 직전 거래 금액 · 계약일 · 층, 구 지수 변화, 시세 보정값 — 모델 입력 그대로, 6-3) | 매주 금요일 (36만 행, 주간 판은 최근 2개 · 월 버전 3개 보관) |
| `trade` | `trade_key`(2-4 해시 + 순번) | 단지 · 면적 · 층 · 동 · 계약일 · 금액 · 거래유형 · 해제 · 등기 · `first_seen` | 매일 (묶음 교체) |
| `region_flow_weekly` | (`week`, `gu`) | 4주 변화 · 순위, 권역 수급 | 매주 |
| `policy_event` | `event_id` | 발표일 · 시행일 · 종류 · 대상 · 출처 URL | 정책 PR 병합 후 `monthly` |
| `pipeline_runs` | (`job`, `partition`, `started_at`) | 상태 · 행 수 · 검사 결과(JSON) | 매 실행 (2-6) |
| `monitoring_monthly` | (`version`, 지표) | 값 · 기준 · 경보 여부 | 매달 (7-3) |
| `events_daily` · `judgment_events` | 날짜 · 종류 · 단지 / 판정 한 건 | 이벤트 수 / 호가 · 적정가 · 판정 단계 (IP 없음) | 요청마다 (6-6 ④, 6-7). **API가 쓰는 유일한 테이블** → API 계정에 이 두 테이블 쓰기 권한만 추가 (5-3) |
| `llm_daily` | (날짜, 버전) | 상담 수 · 비용 · 지연 · 실패율 · 차단 · 피드백 · 채점 | 매일 (7-6) |

- 크기: `fair_price` 36만 행 × 3개 버전 ≈ 110만 행 — 단일 Postgres로 충분 (⑤에서 실제 디스크 사용량 측정)
- 단지명 검색: `pg_trgm` 확장(PostgreSQL 기본 배포의 contrib)으로 단지명 · 주소 부분 일치. 대상이 7,871개라 Elasticsearch는 쓰지 않는다 (3장 기존 결정)
- 범위 하한 · 상한은 `적정가 × exp(lo · hi)`를 만원으로 반올림해 저장한다 → API에서 다시 계산하지 않는다

### 3-3. 엔드포인트 (`analysis-service`, FastAPI)

| 메서드 · 경로 | 용도 | 화면 |
|---|---|---|
| `GET /api/complexes?q=` | 단지명 · 주소 자동완성 (최대 10건) | S1 |
| `GET /api/complexes/{id}` | 단지 프로필 · 태그 · 거래된 전용면적 목록 | S2 |
| `GET /api/complexes/{id}/fair-price?area=` | 그 면적의 층별 적정가 · 범위 (전 층 한 번에) | S2 |
| `GET /api/complexes/{id}/trades?area=&limit=5` | 같은 단지 · 면적 최근 거래 (해제 제외, 해제 건수는 따로) | S2 · S3 |
| `POST /api/judgments` | 호가 판정: `{complex_id, area, floor, asking_price}` → 판정 · 범위 막대 위치 · **설명 단계(6-3)** · 근거 거래 | S3 |
| `GET /api/regions/{gu}/flow` | 구 4주 흐름 · 순위 · 권역 수급 · 정책 타임라인 | S2 |
| `GET /api/meta` | 모델 기준일 · 확정월 · 버전 · 대상(서울 아파트) | 전 화면 안내 |

- **호가는 `POST` 본문으로만** 받는다: URL에 넣으면 접속 로그 · 브라우저 기록에 남는다. 호가는 `judgment_events` 테이블에만 정해진 형태로 남기고(6-6 ④, 12개월), 애플리케이션 로그에는 요청 본문을 남기지 않는다
- 판정 계산: `log(호가 / 적정가)`가 `[lo, hi]` 안이면 "범위 안", 밖이면 벗어난 양이 그 방향 반폭 이하면 "다소", 넘으면 한 단계 위 (11 등급 규칙 · `model_config.json` `grade`). 참고용 행이면 판정 대신 사유를 돌려준다
- 모든 응답에 `version` · `기준일` · `확정월`을 넣는다 → 화면 안내(S3)와 AI 답변이 같은 기준일을 말한다
- **AI 도구 = 이 엔드포인트.** `ai-service`의 도구(단지 조회 · 적정가 · 판정 · 최근 거래 · 지역 흐름)는 위 API를 그대로 호출한다. 정책 문서 검색(RAG)만 `ai-service` 안에 있다 → 4장 평가의 "숫자 정확도 100%"는 답변 숫자 = 이 API 응답으로 검사한다

### 3-4. 응답 시간 · 용량 목표 (추정 → ⑤ k3d 부하 시험으로 확정)

| 항목 | 목표 | 근거 |
|---|---|---|
| 읽기 API 서버 처리 p95 | **200ms 이하** | 기본 키 · 색인 조회만 함. 화면 반응성 기준 INP "좋음" ≤ 200ms ([web.dev INP](https://web.dev/articles/inp))보다 서버가 느리면 화면이 좋은 반응성을 낼 수 없다 |
| 동시 부하 | 초당 10요청에서 위 목표 유지 | 포트폴리오 데모(소수 사용자, Phase 4-4). k6로 S1 → S2 → S3 흐름을 재현해 측정 |
| AI 상담 첫 글자 | ⑤에서 측정해 정함 | 모델 · effort가 4-5 평가로 정해진 뒤에야 의미가 있다 |

- 데이터가 한 주에 한 번 바뀌므로 응답에 `ETag = version + 기준일`을 붙여 브라우저 재요청을 줄인다. 별도 캐시(Redis)는 AI 리포트 · 호출 한도에만 쓴다 (4-4)
- 표 전체를 긁어 가는 요청을 막기 위해 IP별 분당 요청 한도를 Ingress(Traefik)에서 건다. 숫자는 k6로 정상 흐름의 분당 요청 수를 잰 뒤 그 몇 배로 정한다

### 3-5. 참고용(판정 안 함) 처리

| 경우 | 1차 처리 | 근거 |
|---|---|---|
| 신규 단지 (거래 이력 부족) | 범위만, 판정 없음 | 11 등급 규칙 (`new_complex: 등급 없음`) |
| 같은 면적 직전 거래 1년 넘음 · 없음 | **참고용** (범위만, 판정 없음 — 6-6 ① 결정) | 채택 범위 규칙에서도 Test 포함률 67.4% (6-6) |
| 면적 목록에 없는 면적 · 서울 밖 · 아파트 아님 | 선택지에 없음 · 대상 아님 안내 | 3-1, 1-6 |

### 4-3. 상담 1회 비용 (추정 → 실측으로 확정)

상담 1회 = 사용자 질문 1번 → 보통 API 호출 2번 (도구 호출 → 도구 결과 받아 답변).

| 토큰 항목 | 추정 | 비고 |
|---|---:|---|
| 시스템 프롬프트 + 도구 정의 | 3,000 × 2회 | 캐시 읽기 |
| 도구 결과 (적정가 · 범위 · 근거 거래 5건 · 흐름) + 대화 기록 + 질문 | 6,000 | 대화가 길수록 증가 → 세션당 턴 수 제한으로 상한 |
| 출력 (답변 + 생각) | 1,100 | effort에 따라 크게 변함 |

| 모델 | 1회 비용 (추정) | 하루 $0.19로 가능한 상담 | 월 |
|---|---:|---:|---:|
| Sonnet 5.5 | 약 $0.023 (약 33원) | **약 8회** | 약 250회 |
| Haiku 5.5 | 약 $0.0012 (약 2원) | **약 160회** | 약 4,700회 |

→ 월 1만 원이면 **Sonnet 5.5로는 하루 8회뿐**이라 데모로도 부족하다. Haiku 5.5는 약 20배 싸다.
→ 단, 싼 모델이 품질을 지키는지는 가정하지 않는다. **4-5 평가 세트로 두 모델을 같은 기준에서 비교하고, 기준을 통과한 것 중 싼 모델**을 쓴다 (ML 모델 교체와 같은 원칙).

### 4-4. 호출 한도 (모델 확정 뒤 숫자 확정)

한도는 겹으로 둔다. 숫자는 `하루 가능 상담 수 = $0.19 ÷ 실측 1회 비용`에서 나온다.

| 한도 | 규칙 | Haiku 5.5일 때 (추정) | Sonnet 5.5일 때 (추정) |
|---|---|---|---|
| **하루 전체 비용 상한** (핵심) | 응답 `usage`(입력 · 캐시 읽기/쓰기 · 출력)로 실제 금액을 누적, 넘으면 그날 AI 중지 → ML 카드만 표시 + "오늘 AI 상담 한도 소진" 안내 | $0.19 | $0.19 |
| 월 상한 | 월 누적 $5.7 넘으면 그 달 AI 중지 | — | — |
| IP별 하루 | 한 사람이 하루 예산을 다 쓰지 못하게 (하루 가능 수의 약 1/8) | 20회 | 1회 |
| 세션별 | 대화 길이 · 입력 토큰 상한 | 10턴 | 3턴 |
| 리포트 캐시 | 같은 단지 · 면적 · 월 리포트는 다시 생성하지 않음 | 적용 | 적용 |

- 누적 금액은 Redis 일 · 월 카운터 (서버 재시작에도 유지되도록 Postgres에 일 1회 기록). 가격표는 설정 파일로 두고 가격이 바뀌면 설정만 고친다
- 한도 소진 · 실패 시에도 적정가 · 범위 · 판정 · 근거 거래는 그대로 보인다 (12장 LLMOps 장애 대응)
- Sonnet 5.5만 통과한다면 하루 8회로는 데모가 어렵다 → 예산 상향 또는 "리포트만 AI · 대화는 제한" 같은 범위 조정을 그때 사용자와 다시 정한다

### 4-5. 모델 선택 절차 · 평가 세트

1. **평가 세트 만들기** (질문 · 정답 50~100개, 12장): 단지 적정가 설명, 호가 판정 설명, 참고용 단지, 투자 권유 요청("살까요?"), 도구에 없는 숫자를 묻는 질문, 대출 · 규제 질문(출처)
2. **채점 기준 (결과 전에 고정)**
   - 숫자 정확도: 답변 속 숫자 = 도구 결과 → **100%** (코드 검사)
   - Guardrail 위반(투자 권유 · 미래 단정 · "감정가"): **0건**
   - 정책 답변 출처 포함률 · 한국어 자연스러움: LLM-as-judge + 표본 직접 확인, 기준은 평가 세트 만들 때 정함
3. **같은 세트로 Haiku 5.5와 Sonnet 5.5 실행** → 기준 통과 모델 중 1회 비용이 낮은 모델 선택, effort도 `low`부터 올려 가며 통과하는 가장 낮은 값
4. **실측으로 4-3 · 4-4 숫자 확정**: `count_tokens` + 응답 `usage`로 1회 비용의 평균 · 90% 값을 재고, 한도는 90% 값으로 계산
5. **개발 · 평가 비용 (별도, 사용자 동의 2026-11-18):** 평가 세트 100문항 1회 실행 추정 Sonnet 약 $2.3 · Haiku 약 $0.12 → **개발 중에는 20문항 표본**(Sonnet 약 $0.46 · Haiku 약 $0.02)으로 돌리고, **전체 실행은 모델 · 프롬프트를 확정할 때만**. 개발 기간 전체 몇천 원 수준으로 본다. 개발용 API 키는 서비스 키와 나눠 사용량을 따로 본다

**단계:**
1. **⑤ 공개 직전에 AWS 계정을 만든다** — 크레딧 6개월이 계정 생성일부터 줄어든다
2. **Terraform으로 AWS 구성**: EC2 t4g.large · 보안 그룹(80 · 443 · 내 IP 22) · S3 백업 버킷 · **IAM 역할**(EC2가 키 없이 S3에 씀 → 5-3 "백업 저장소 키"가 AWS 단계에서는 필요 없음) → 그 위에 k3s + Helm + Argo CD (5-6)
3. **EKS 짧은 검증**: 같은 Terraform · Helm 차트로 EKS를 몇 시간 띄워 접속 · k6 간단 부하 시험 · 화면 기록 후 `terraform destroy`. 비용 약 $1 (**추정**: 컨트롤 플레인 $0.10/시간 + 노드 $0.104/시간 + 부대 비용) → "같은 차트가 k3s와 EKS에서 그대로 돈다"는 이식성 근거
4. **크레딧 소진 · 만료 2주 전에 Oracle A1으로 이전**: Terraform(OCI) + 5-6 구축 절차 + 백업 복원 → DNS 전환. 같은 ARM이라 이미지를 그대로 쓴다. **중단 시간을 실측해 기록**한다 (5-4 복구 시험을 실제 이전으로 한 번 더 증명)
- **ARM(t4g · A1)을 택해 지는 부담** (이미 설계에 있음): 이미지를 amd64 · arm64 두 가지로 빌드(5-6, 로컬 PC가 x64), `apt-core` 테스트 · 재학습 재현(T5)을 arm64 CI에서도 확인(1-4, 1-5)
- Oracle A1을 만들 수 없거나 회수되면 그때 대체 후보 가격을 다시 확인하고 가장 싼 것으로 옮긴다 (현재 기준 Lightsail 8GB)
- 쿠버네티스(k3s)는 두 단계 모두 같은 구성이다. 메모리는 8GiB(t4g.large)에서도 최대 약 5.6GiB로 들어간다 (5-1)
- 크레딧 기간 뒤 고정비로 남는 것은 **도메인뿐**이다 (5-5, 5-8)

**Terraform**: 서버 · 디스크 · 방화벽 · 저장소 · 권한을 코드 파일로 적어 두고 `terraform plan`(미리 보기) → `apply`(만들기) → `destroy`(지우기)로 다루는 도구. 앱(k3s 위의 파드)은 지금처럼 Helm · Argo CD가 맡고, Terraform은 그 아래 서버 층만 맡는다
- 위치: `infrastructure/terraform/aws/` · `infrastructure/terraform/oci/`. 개발 PC에서 실행하고 클러스터 안에는 아무것도 띄우지 않는다 (메모리 영향 없음)
- 상태 파일(`terraform.tfstate`)에는 리소스 정보 · 비밀값이 들어갈 수 있어 **Git에 넣지 않는다**(`.gitignore`). 1인 작업이라 개발 PC 로컬에 두고, 암호화 저장소에 백업한다 (봉인 키와 같은 곳, 5-3)
- AWS · OCI API 자격 증명은 개발 PC 환경 변수로만 쓰고 Git · 채팅 · 명령 인자에 남기지 않는다

### 5-1. 자원 실측 (2026-11-18, 로컬 Docker 안 k3s 컨테이너, x64 8코어)

k3d 대신 같은 내용물인 `rancher/k3s` 컨테이너를 띄우고, 1차에 쓸 플랫폼 구성 요소를 공식 매니페스트 · 이미지로 올려 쟀다. 앱(`analysis` · `ai` · `frontend`)은 아직 없어 빠졌고, 모든 구성 요소가 **요청 없는 빈 상태**다.

| 구성 (버전) | 컨테이너 메모리 (`docker stats`, 3회) | 프로세스 메모리 (cgroup `anon`) |
|---|---|---|
| k3s 기본 (v1.34.1+k3s1: CoreDNS · Traefik · local-path · metrics-server) | **약 690MiB** | — |
| + Argo CD v3.6.1 (전체 설치) · cert-manager v1.21.3 · Sealed Secrets v0.41.2 · Postgres 17.12 · Redis 8.10.3 · Qdrant 1.20.2 | 약 1.8GiB | 약 1.2GiB |
| + Postgres에 서빙 테이블 크기 데이터 적재 (아래 5-2) | **약 2.2GiB** | 약 1.2GiB |

- **Oracle 무료 VM 회수 기준과 메모리** ([OCI Always Free](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm), 2026-11-18 조회): 7일 동안 다음이 참이면 회수될 수 있다 — CPU 95번째 백분위 20% 미만, 네트워크 20% 미만, **메모리 20% 미만(A1만)**
  - 데모 사용량으로는 CPU · 네트워크 조건은 거의 확실히 참이다 → **회수를 막는 것은 메모리뿐**이고, 12GB의 20%는 2.4GiB다

### 5-4. 백업 · 복구

무엇을 잃으면 다시 만들 수 없는지부터 나눈다.

| 상태 | 잃으면 | 백업 |
|---|---|---|
| 코드 · Helm 차트 · 정책 CSV · `SealedSecret` | GitHub에 있음 | 없음 (Git) |
| 클러스터 설정 (배포된 리소스) | Argo CD가 Git에서 다시 만든다 | 없음 (GitOps) |
| 봉인 개인 키 | `SealedSecret`을 못 푼다 | 5-3 (개발 PC, 월 1회) |
| **Postgres** | `first_seen`(처음 본 날짜, 2-4) · `pipeline_runs` · 모델 버전 이력 · OOF 잔차는 API 재수집으로 **되살릴 수 없다** | **`backup-daily` CronJob: `pg_dump` → 객체 저장소** |
| 모델 파일 · 월 스냅숏 (`snapshot-monthly`, 2-2) | 같은 데이터 · 같은 플랫폼이면 재학습으로 같은 트리 (1-5) — 그러려면 그 달의 스냅숏이 있어야 한다 | 매달 객체 저장소로 복사 |
| 수집 원본 | 최근 13개월은 다시 받을 수 있지만 해제 상태가 바뀐다 | 월 스냅숏에 포함 |

- 백업 위치: **AWS 단계 = S3**(EC2 IAM 역할로 접근, 5-0), **Oracle 단계 = OCI Object Storage (무료 20GB · 월 API 요청 5만 건**, [OCI Always Free](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)). 보관: 일 7개 + 월 12개 × 약 25MB(5-2 실측, 실제 데이터로 재측정) + 월 스냅숏 · 모델 → 수 GB 이내 예상. 요청은 하루 몇 건이라 한도의 1% 미만
- 백업 Job은 **S3 호환 API**로 작성해 두 저장소에서 설정만 바꿔 쓴다. 이전할 때는 S3의 백업을 OCI로 복사한 뒤 AWS 계정을 정리한다
- **복구 시험을 설계에 넣는다**: ⑤에서 빈 k3d 클러스터에 5-6 "새 VM 구축" 절차 + 봉인 키 복원 + `pg_restore`를 실제로 해 보고 걸린 시간을 기록한다 (DB 복구만은 17초 실측). 복구해 본 적 없는 백업은 백업으로 치지 않는다
- 한계: 백업 버킷이 VM과 같은 OCI 계정이라 **계정 자체를 잃으면 함께 잃는다** → 월 백업 1개를 개발 PC에도 받아 둘지는 ⑤에서 정한다 (DB에는 공개 실거래 · 모델 출력과, 개인 식별 정보 없이 저장한 판정 이벤트(호가, 6-6 ④)가 있다. 대화 원문은 DB에 없다)

### 5-5. 네트워크 · 도메인 · TLS

- 외부에 여는 포트는 **80 · 443만**. SSH(22)는 내 IP만 허용, k3s API(6443) · Argo CD 화면은 외부에 열지 않고 SSH 터널(`kubectl port-forward`)로만 쓴다
- TLS: cert-manager + Let's Encrypt (Traefik으로 HTTP-01 검증). [Let's Encrypt 한도](https://letsencrypt.org/docs/rate-limits/): 등록 도메인당 7일 50개, 같은 이름 묶음 7일 5개, 검증 실패 시간당 5회 → 설정은 **스테이징으로 먼저 시험**(공식 권장)하고 성공 후 운영 발급으로 바꾼다
- **도메인이 필요하다**: Let's Encrypt 한도는 Public Suffix List 기준 등록 도메인 단위로 세므로, `sslip.io` 같은 공용 와일드카드 DNS를 쓰면 한도를 다른 사용자와 나눌 수 있다(공식 문서는 이런 서비스의 예외를 언급하지 않음) → **도메인 구입은 사용자 결정**, 비용은 연 1~2만 원대 **추정**(구입 시 확인)
- IP별 요청 한도는 Traefik 미들웨어로 건다 (3-4, 숫자는 k6 측정 후)

### 5-6. 배포 절차 (GitOps)

| 단계 | 내용 |
|---|---|
| 1. CI (GitHub Actions, develop push) | `apt-core` 테스트 T1~T9 (x64 · arm64, 1-4) → 서비스별 이미지를 buildx로 **amd64 · arm64 함께** 빌드 → GHCR에 `:git SHA`와 `:앱 버전` 태그로 올림. 같은 버전 태그가 이미 있으면 덮어쓰지 않고 실패 |
| 2. 배포 결정 | 단계 결과 커밋에서 Helm `values-prod.yaml`의 이미지 버전을 올린다 → 사람의 커밋이 곧 배포 기록 (봇 커밋을 만들지 않아 커밋 규칙과 충돌 없음) |
| 3. Argo CD | develop의 `infrastructure/helm/`을 보고 자동 동기화(`selfHeal` · `prune`). 앱 Deployment는 `RollingUpdate`, `maxUnavailable: 0` → 이미지 빌드가 끝나기 전에 동기화돼도 새 파드가 뜰 때까지 옛 파드가 계속 서비스한다 |
| 4. DB 변경 | Alembic 마이그레이션을 Argo CD PreSync Job으로 실행. 옛 · 새 파드가 잠시 함께 돌므로 **추가 → 전환 → 삭제** 순서로 나눠 하위 호환 유지 |
| 5. 확인 | `/api/meta`의 앱 버전 · 모델 버전 확인 + S1 → S3 흐름 점검 (k6 스크립트 재사용) |

- **코드 되돌리기** = 이미지 버전을 올린 커밋을 되돌림 → Argo CD가 옛 버전으로 동기화
- **모델 되돌리기는 배포가 아니다** = `serving_current`를 이전 버전으로 바꾸는 한 줄 (2-5, 보관 3개)
- 파이프라인 CronJob도 같은 `apt-core` 이미지 버전을 쓴다 → 학습 · 서빙 코드 버전이 어긋나지 않는다
- **새 VM 구축 (= 장애 복구 절차 = AWS → Oracle 이전 절차)**: ① **Terraform `apply`**로 VM · 방화벽(80 · 443 · 내 IP 22) · 백업 저장소 · 권한 생성 (5-0) ② k3s 설치(버전 고정) ③ Sealed Secrets 설치 + 봉인 키 복원 ④ Argo CD 설치 후 앱 묶음(app-of-apps) 등록 → 나머지는 Git에서 자동 ⑤ 백업에서 `pg_restore` ⑥ DNS를 새 IP로. ⑤에서 이 순서로 k3d에 실제로 세워 보고 단계별 명령을 스크립트로 남긴다

### 5-7. 관측 · 알림 (작게)

- Prometheus · Grafana 묶음은 1차에 쓰지 않는다: 데모 규모에서 볼 지표가 적고, 판단에 필요한 것은 파이프라인 결과 · 가동 여부 · AI 비용이다
- **파이프라인**: `pipeline_runs`(2-6)에 모든 실행을 기록. 실패하면 Job 마지막 단계에서 알림. **"실행되지 않음"도 잡는다**(CronJob은 실행을 건너뛸 수 있다, Phase 4-4) → 감시 작업이 매일 06:00에 그날 `collect-daily` 성공 기록이 없으면 알림
- **가동 확인**: GitHub Actions 예약 실행으로 `/api/meta`를 1시간마다 호출. [공식 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows): 최소 간격 5분, 부하 시 지연 가능, **공개 저장소는 60일 활동이 없으면 예약 실행이 꺼진다** → 데모 감시용으로만 쓰고 지연은 감수, 60일 규칙은 월 1회 이상 커밋 · 정책 PR로 피한다
- **AI 비용**: 4-4 일 · 월 누적 금액, 상한의 80% 도달 시 알림 + Langfuse
- **AWS 크레딧 · 요금**: AWS Budgets로 크레딧 잔액 · 예상 청구 알림, 크레딧 소진 · 만료 2주 전 알림 → Oracle 이전 시작 (5-0)
- **VM 메모리 사용률**: 25% 아래면 알림 (5-1 회수 기준)
- 알림 채널: **디스코드 (사용자 결정 2026-11-19)**. 개인 서버에 알림 전용 채널을 만들고 웹훅 URL로 보낸다. 파이프라인 · 감시 Job · AI 비용 · 가동 확인(GitHub Actions) · Argo CD notifications(5-1에서 이미 떠 있음)가 모두 같은 웹훅을 쓴다. AWS Budgets 알림은 메일로 오므로 그대로 받는다
  - 알림 문구에는 작업 이름 · 상태 · `pipeline_runs` id 정도만 넣고, 비밀값 · 호가 · 대화 원문은 넣지 않는다
- 앱 로그는 표준 출력 → k3s 컨테이너 로그(로테이션)로만 둔다. 요청 본문은 남기지 않는다 (5-3)

### 5-9. 못 막는 것 (한계)

- 단일 노드라 VM이 멈추면 서비스도 멈춘다 (Phase 4-4: 고가용성 아님). 복구는 5-6 절차로 사람이 한다
- Oracle이 A1을 회수하거나 용량 부족으로 다시 만들지 못하면 유료 VM으로 옮겨야 한다 (현재 기준 가장 싼 후보 Lightsail 8GB $44/월, 5-0)
- AWS 크레딧이 $100만 나오면 AWS 단계는 약 1.5개월이다. 무료 플랜에서 t4g.large를 막으면 유료 플랜 전환이 필요하고, 그때부터는 크레딧을 넘는 청구 위험이 생긴다 (5-0 Budgets 알림 · 자동 중지로 대비)
- 5-1 측정은 빈 상태 · x64 · Docker 안이다. ARM VM · 실제 데이터 · 부하 상태 값은 ⑤에서 다시 잰다

### 5-10. 1차 구현 범위 (결정 2026-11-25)

기준: **"공개 뒤로 미루면 되돌릴 수 없이 잃는 것이 있나?"** — 있으면 1차, 없으면 1.1(공개 직후). 설계(1 ~ 7장)는 그대로 두고 구현 순서만 정한다.

| 구분 | 1차 | 1.1로 (미뤄도 잃는 것 없음) |
|---|---|---|
| 서비스 | `apt-core` + 일치 테스트 T1 ~ T9, S1 ~ S4 (**AI 상담 포함**), analysis API, ai-service | (2차 그대로) 단지 비교 · 지도 · 스크리너 |
| 파이프라인 | `collect-daily` · `index-weekly` · `predict-weekly` · `monthly`, 품질 게이트, 모델 버전 3개, OOF(서빙한 입력 기준, 2-1) | 공식 API 자동화 — 공시가격(브이월드) · 학원(상가정보 OpenAPI) · 학교알리미 API (1차는 연 1 ~ 4회 수동, 2-2 "수동 작업"), 정책 이벤트 **LLM 행 초안 · 자동 PR** |
| 규제 · 정책 | **보도자료 감지 + 디스코드 알림**(주 1회, 공식 API · RSS, 아래) → 사람이 원문 확인 후 정책 CSV 갱신 → 다음 `monthly` 반영 | — |

| 안전장치 | 포함률 · MAPE 경보(7-3), AI 답변 전 숫자 · 금지 표현 검사, LLM CI 평가, 호출 한도(4-4), 백업 + 복구 시험, 디스코드 알림 | PSI 드리프트 묶음 감시, LLM 표본 채점(`llm-eval-daily`) — 1차는 피드백 · CI 평가로 대신 |

- 1.1로 미뤄 바뀌는 것: 5-6 배포 3 · 4단계(Argo CD 동기화 · PreSync 마이그레이션)는 1차에서 `helm upgrade` + 마이그레이션 Job 수동 실행으로, 클러스터 설정 복구는 Git의 Helm 차트 재설치로 한다. 상시 메모리는 Argo CD 약 155MiB · Sealed Secrets 약 10MiB만큼 줄어든다(5-1)

- **규제 감지를 1차에 넣는 이유 (2026-11-25, 사용자 제기):** 정책 이벤트는 2025년 44건 · 2026년 1 ~ 9월 34건으로 한 달 평균 3 ~ 4건이고, 한 달에 10 ~ 14건이 몰린 달도 있다(2025-06 · 10, 2026-08). 정책은 모델 Feature 41개(가장 큰 묶음)와 정책 타임라인 화면을 바꾸므로, 놓치면 그 지역 적정가 · 판정이 틀린 채로 서빙된다 — 1차 기준의 '안전장치'에 해당한다. 출처는 금융위 62 · 국토부 45 · 서울시 25 · 기재부 18 · 행안부 14건(`housing_policy_events_v2.csv`). 반영은 계속 사람 승인이다 (토허 단지 범위처럼 원문 해석이 필요하고, 잘못 넣으면 전체 거래 Feature가 틀어진다, 2-2)
- **지금 할 일:** 정책 CSV는 2026-10-08 이후 갱신되지 않았다(마지막 발표일 2026-09). ② 첫 실행 전에 2026-10월 이후 발표분을 채워 넣는다
- **학군 데이터:** 학교 통계(EDSS · 학교알리미, 모델 Feature)는 연도별 원천이 남아 있어 스냅숏이 필요 없다 — 1차는 연 1회 수동 갱신. **학구도(통학구역 · 중학교 학구)는 최신판만 받을 수 있어**(공공데이터포털 파일 데이터, 스냅숏 시작 때 확인) `snapshot-monthly`에 넣는다. 화면은 S2 단지 프로필에 배정 초등학교 · 중학교 학구를 표시값으로 보여 준다 (모델 Feature 아님 — 11 보완 2에서 불채택). 학원(상가정보)은 분기 파일이 과거분까지 남아 스냅숏이 필요 없다. 유치원 목록도 유치원알리미 공시 자료가 공시차수별(2013년 1차 ~)로 남아 있어 스냅숏에서 뺀다 — V2의 "폐원 유치원 복원 불가" 한계를 이 자료로 풀 수 있는지는 별도 과제(확인 2026-11-25)
- `snapshot-monthly`는 서비스 공개 전부터 개발 PC에서 매달 돌리고, 공개 뒤 CronJob으로 옮긴다. 저장 위치 · 실행 방법은 스냅숏 스크립트에 적는다

## 6. 화면 · 기획서 13장 결정 · 사용성 테스트

### 6-1. 원칙

- **휴대폰이 먼저다**: 사용 순간이 "매물 사이트나 중개사무소에서 호가를 보고 판단할 때"(기획서 2장)라 좁은 화면에서 S2 → S3가 한 손으로 끝나야 한다. 넓은 화면은 같은 구성을 두 단으로 펼친다
- **숫자 하나보다 범위**: 적정가 중심값은 작게, 범위를 크게 (기획서 3장 약속 1, 11장 "상승장 과소추정" 대응)
- **모든 숫자에 기준일**: 화면의 숫자는 3-3 API 응답 그대로이고, 응답의 `version` · `기준일` · `확정월`을 화면 하단에 항상 표시한다
- **화면 · 판정 · AI가 같은 숫자**: 화면은 계산하지 않는다. 판정 · 참고용 여부 · 범위는 모두 API(= 미리 계산한 표, 3-1)에서 온다
- 대상 범위를 첫 화면에 밝힌다: "서울 아파트만 · 모델 추정 적정가 (감정평가 아님)"

### 6-2. 화면별 구성과 API

| 화면 | 보여 줄 것 | API (3-3) |
|---|---|---|
| **S1 검색** | 단지명 · 주소 자동완성(최대 10건, 구 · 세대수 · 준공연도 함께), 많이 본 단지 | `GET /api/complexes?q=` · 많이 본 단지는 6-7 이벤트 집계 |
| **S2 단지 분석** | ① 단지 프로필 · 태그 · 배정 초등학교 · 중학교 학구(학구도 표시값, 5-10) ② 전용면적 선택(5년간 거래된 면적만, 3-1) ③ 그 면적의 **층 묶음별 적정가 범위**(6-5) ④ 같은 단지 · 면적 최근 거래 5건(해제 건수는 따로) ⑤ 구 4주 흐름 · 순위 · 권역 수급 · 정책 타임라인 ⑥ "호가 판정하기" 버튼 | `/complexes/{id}` · `/fair-price?area=` · `/trades` · `/regions/{gu}/flow` |
| **S3 호가 판정** | 입력(면적 · 층 · 호가) → **판정 카드**: 판정 문구(6-3) · 범위 막대 위 호가 위치 · 적정가와의 차이(%) · **설명 단계(6-3)** · 근거 거래 · 안내 문구(6-4) · "왜 이렇게 나왔어?" 버튼 | `POST /api/judgments` |
| **S4 AI 상담** | 리포트(요약 · 가격 요인 · 확인할 점), 대화, 정책 답변의 출처 링크. 답변은 끝까지 받아 검사한 뒤 표시(7-5) | `ai-service` (도구 = 3-3 API) |

- 호가 입력은 "억 · 천만" 단위 입력을 돕는다(예: `12억 3천` → 123,000만 원 미리 보기). 잘못 친 자릿수가 판정을 망치는 가장 흔한 실수일 것이라(추정) 입력값을 판정 카드 위에 다시 보여 준다
- S3에서 면적 · 층은 S2에서 고른 값을 이어받는다. 층은 1 ~ 그 단지 최고층만 고를 수 있다 (`fair_price`에 있는 행만)

### 6-3. 판정 카드 문구 (기획서 13장 결정 ② — 결정 2026-11-20)

판정 계산은 3-3 그대로다(`log(호가/적정가)`가 범위 안 / 밖이면 반폭 대비). 문구는 **비교 기준을 밝히는 형태**로 쓴다 — 모델은 실거래가로 학습했고 호가는 보통 실거래보다 높게 나오기 때문이다(기획서 7장). 손으로 캡처한 표본에서는 매물평균가가 적정가보다 중앙 3.8% 높았다 ([asking-price-check.md](asking-price-check.md) §8).

| 조건 | 판정 문구 | 보조 문구 |
|---|---|---|
| 범위 안 | **적정 범위 안** | 실거래 기준 모델 추정 적정가 범위 안입니다 |
| 위로 벗어남 ≤ 반폭 | **다소 높은 편** | 실거래 기준 적정가 범위보다 조금 높습니다 |
| 위로 벗어남 > 반폭 | **높은 편** | 실거래 기준 적정가 범위보다 높습니다 |
| 아래로 벗어남 ≤ 반폭 | **다소 낮은 편** | 실거래 기준 적정가 범위보다 조금 낮습니다 |
| 아래로 벗어남 > 반폭 | **낮은 편** | 실거래 기준 적정가 범위보다 낮습니다. 급매 · 하자 · 조건 차이가 있는지 확인해 보세요 |
| 참고용 | **판정하지 않음 (참고용)** | 사유(6-4)와 범위만 표시 |

- "고평가 · 저평가 · 싸다 · 비싸다 · 사세요"는 쓰지 않는다 (기획서 7장, 7-5 금지 표현과 같은 목록)
- 색은 판정의 좋고 나쁨을 암시하지 않게 중립색 단계로 하고, **색만으로 구분하지 않는다**(문구 · 막대 위치를 함께, 6-8)
- "낮은 편"의 보조 문구는 판단을 권하지 않고 확인할 점만 말한다 (기획서 8장 "판단 대신 확인할 점")

|---|---|---|
| ① 직전 거래 | 같은 단지 · 면적 마지막 중개거래 (계약일 · 층 · 금액) | `fair_price` 설명 근거 = 모델 입력 `직전거래가_동일면적` |
| ② 구 시세 변화 | 그 거래 주 → 기준일 전 공표 주의 구 주간 지수 변화(%), "시세 변화만 반영하면 약 ○억" | 모델 입력 `직전거래후_구지수변화` · `직전거래가_시세보정` |
| ③ 모델 보정 | 적정가 ÷ ②의 값 − 1 (%) — 층 · 단지 특성 · 시장 지표로 모델이 더한 차이. 요인 설명은 "왜 이렇게 나왔어?"(AI) | 적정가 · ② |
| ④ 적정가와 호가 | 모델 추정 적정가 · 80% 범위, 호가와의 차이 "+x%" | `fair_price` · 판정 계산(3-3) |

- ① · ②는 모델 입력 값을 그대로 보여 준다 → 화면 숫자와 모델 숫자가 어긋나지 않는다 (12장 "숫자는 ML"). 값은 `monthly` · `predict-weekly`가 적정가와 함께 `fair_price`에 저장한다(3-2). 매주 새로 신고된 거래가 ①에 들어온다
- 기준일 뒤에 생긴 같은 면적 거래는 ①을 바꾸지 않고, 근거 거래 목록에 "기준일 이후 거래"로 따로 보여 준다 (적정가에는 다음 달 반영)
- 참고용(직전 거래 1년 넘음 · 없음, 신규 단지)은 ①이 없거나 믿기 어려워 설명 단계를 보여 주지 않는다
- ③을 넣는 이유: 표본 28개에서 모델 적정가와 단순 계산(① × ②)의 차이가 5% 넘는 단지 12개, 10% 넘는 단지 4개 → 숨기면 "직전 거래보다 왜 다르냐"를 알 수 없다
- 문구 이해도는 6-9 사용성 테스트에서 확인한다

### 6-7. 지표 수집 (기획서 10장)

- 외부 분석 도구(구글 애널리틱스 등)는 1차에 쓰지 않는다: 쿠키 · 동의 화면이 필요해지고, 필요한 지표가 몇 개뿐이다
- `analysis-service`가 이벤트를 하루 단위로 센다 → `events_daily`(날짜 · 종류 · 단지 · 수): 단지 페이지 조회, 판정 요청, 판정 단계별 수, AI 상담 시작, 피드백. **IP는 넣지 않는다**. 판정 한 건 한 건(호가 포함)은 따로 `judgment_events`에 남긴다 (6-6 ④)
- 판정 완료율 = 판정 요청 ÷ 단지 페이지 조회 (기획서 10장 정의). "많이 본 단지"(S1)도 이 표에서 나온다
- 응답 시간 지표: 기획서 10장의 "AI 첫 토큰 3초"는 **7-5에서 스트리밍을 하지 않기로 해 의미가 바뀐다** → "AI 답변 표시까지 시간"으로 바꾸고, 목표는 ④에서 실측한 뒤 정한다. 판정 카드 1초는 유지 (DB 조회 0.1ms 미만, 5-2 → API · 네트워크 시간이 대부분, k6로 확인)

### 6-8. 프론트엔드 기술 · 접근성

- **React + Vite로 정적 파일을 빌드해 nginx 컨테이너로 서빙**(SPA). 노드 서버가 없어 메모리가 거의 들지 않는다(5-1 예산의 "앱 3개 약 0.5GiB 추정" 안)
  - 대신 단지 페이지가 검색 엔진에 잘 잡히지 않는다(SPA). 1차는 포트폴리오 데모라 검색 유입이 목표가 아니므로 감수하고, 검색 유입이 필요해지면 서버 렌더링(Next.js 등)을 2차에 검토한다
- 접근성: 글자 · 배경 대비 WCAG AA, 범위 막대는 색 외에 문구 · 숫자로도 읽히게, 입력 · 버튼은 키보드와 화면 낭독기 이름표 지원. 공개 전 점검 목록으로 확인
- 화면 문구는 한 곳(문구 파일)에 모아 6-9 테스트 뒤 고치기 쉽게 한다

### 6-9. 사용성 테스트 (기획서 12장)

| 확인할 것 | 성공 기준 |
|---|---|

### 7-1. ML 변경은 두 종류다

| 종류 | 예 | 승격 방법 |
|---|---|---|
| **월 갱신** (같은 설정) | 매달 m-2월까지 데이터로 다시 학습 | 자동. 2-6 게이트 통과 시 공개. 새 모델의 성능은 2개월 뒤 그 달 거래가 확정되어야 알 수 있다 → 7-3 OOF 감시가 사후 평가 |
| **설정 변경** | Feature 추가 · 파라미터 · 범위 규칙 · 알고리즘 | **두 단계를 모두 통과해야 교체** |

설정 변경의 두 단계 (기준은 결과 전에 고정, V2 · V3에서 쓴 규칙 그대로):
1. **오프라인 실험**: 운영과 같은 lr · 트리 수, 평가 데이터로 조기 종료하지 않음, 먼저 seed 편차 확인 → 시간 폴드 4개 × seed 3개에서 기존 설정보다 나음 (보완 5 규칙)
2. **섀도 운영 3개월**: `monthly`가 챌린저도 함께 학습 · 예측해 OOF를 저장만 하고 서빙하지 않는다. 3개월 중 2개월 이상 + 3개월 평균에서 중개 OOF MAPE가 챔피언보다 낮고, 80% 범위 포함률이 7-3 하한 위면 교체
- 섀도 비용: 재학습이 한 번 더 늘 뿐(약 2분, 1-5). 챔피언 다음에 차례로 돌려 메모리 최대치는 그대로 (5-1)
- 섀도 기간이 3개월인 이유: OOF가 확정되는 데 2개월이 걸리고(2-5), 월별 MAPE 표준편차 0.53%p(2-6)에서 한 달만으로는 우연을 가르기 어렵다

### 7-2. 실험 추적 · 모델 기록 · 계보 — MLflow는 서버 없이 쓴다 (실측)

| 측정 (2026-11-18, Docker, MLflow v3.18.0 공식 이미지, 빈 상태) | 메모리 |
|---|---|
| `mlflow server` 기본 설정 | **2.4GiB** |
| `--workers 1` | **1.84GiB** (MLflow 3의 백그라운드 작업 실행기 huey 프로세스 3개 · 각 약 240MB가 계속 떠 있음) |

- 상시 서버로 두면 5-1 상시 예산(약 3.2GiB)이 약 5GiB로 늘고, 8GB VM에서는 재학습 때 여유가 없다 → **MLflow를 라이브러리로만 쓴다**: `monthly` Job이 MLflow 클라이언트로 **Postgres(`mlflow` 스키마)에 직접 기록**하고, 모델 파일은 작업용 PVC + 백업 버킷(5-4)에 둔다. 화면(UI)은 볼 때만 개발 PC에서 `mlflow ui`를 Postgres 포트 포워딩에 붙여 띄운다 → **상시 메모리 0**
  - 클라이언트가 서버 없이 DB에 직접 쓰는 구성은 ① 단계에서 실제로 확인한다. 안 되면 서버를 Deployment `replicas: 0`으로 두고 볼 때만 1로 올린다
- 매달 실행 하나에 남기는 것 (계보):

| 항목 | 내용 |
|---|---|
| 데이터 | 학습 확정월, 학습 행 수, 사용한 묶음의 `pipeline_runs` id · 묶음 해시 |
| 코드 | 이미지 버전 · git SHA, 레지스트리(`v2_feature_registry.csv`) 해시, `model_config.json` 해시 |
| 환경 | 아키텍처(arm64 / x64), LightGBM · numpy · pandas 버전 (1-5: 시스템이 다르면 결과 보장 없음) |
| 결과 | 트리 수, 게이트 결과, 전 달 대비 적정가 변화 중앙값, 2개월 뒤 채워지는 OOF MAPE · 범위 포함률 |
| 산출물 | 모델 파일, 범위표, 일괄 예측 요약 |

- 서빙 기준은 계속 `serving_current`(3-2)다. MLflow는 **기록**이고, 서빙을 결정하지 않는다 (진실 공급원은 하나)
- 오프라인 실험(7-1의 1단계)도 같은 MLflow 형식으로 개발 PC의 로컬 저장소에 남긴다. V2 · V3의 실험 기록(CSV + README 행)은 그대로 둔다

### 7-3. ML 감시 지표와 기준 (과거 데이터에서 정함, 결과 전에 방식 고정)

방식은 2-6 MAPE 경보와 같다: **최근 24개월 평균 ± 3σ**. 측정은 `oof_predictions.parquet`(중개, 2022-05 ~ 2026-06 · 월 50개) · `v2_trade.parquet`, 2026-11-18.

| 지표 | 과거 분포 | 경보 | 경보가 울리면 |
|---|---|---|---|
| 중개 OOF MAPE (m-2월) | 최근 24개월 평균 4.79% · σ 0.53 | **> 6.4%** | 2-6 그대로 (자동 되돌림 없음) |
| **80% 범위 실제 포함률** (채택 규칙: 단지 × 가격대 × 단지 최근 흐름) | 최근 24개월 평균 **80.0%** · σ 3.84 · 최저 72.6 · 최고 86.6 (월 거래 중앙 3,503건, 순수 표본오차 σ는 0.68%p뿐 → 흔들림은 대부분 시장 변화) | **< 68.5%** 또는 **> 91.5%** | 아래로: 화면에 "최근 시장 변동이 커 범위 정확도가 평소보다 낮습니다" 안내를 다시 기준 안으로 들어올 때까지 표시 (사용자에게 솔직히). 위로: 범위가 너무 넓다는 뜻 → 다음 범위 규칙 검토 거리 |
| 드리프트: **안정형 Feature 74개** | 42개월 동안 PSI > 0.25인 달이 한 번도 없음 (PSI 중앙 0.01 · p99 0.17 · 최대 0.25) | **PSI > 0.5** (과거 최대의 2배) | 원천 데이터 오류 의심 → 그 Feature 출처 점검. 공개는 2-6 게이트가 판단 |
| 드리프트: **시간 변동형 Feature 91개** | 금리 · 지수 · 경과월 등, 매달 절반 넘게 PSI > 0.25 → PSI는 의미 없음 | 경보 없음, 대신 **학습 범위 밖 값** 목록을 월 보고서에 표시 (값의 절반 넘게 학습 min~max 밖인 Feature 수: 월 중앙 6 · 최소 2 · 최대 30) | 트리 모델은 학습 범위 밖을 외삽하지 못한다 → 목록이 길어지는 달은 MAPE · 포함률과 함께 본다 |
| 중간형 36개 | PSI > 0.25인 달 비율 중앙 13% | 경보 없음, 월 보고서에 상위 표시 | — |

- **PSI 경보를 Feature마다 흔한 0.25 기준으로 걸지 않는다**: 그렇게 하면 매달 201개 중 81~114개가 경보다(측정). 감시가 매달 울리면 아무도 보지 않는다 → Feature를 과거 이력으로 세 묶음으로 나눴다. 묶음은 지금 고정하고, 새 Feature를 추가할 때 같은 방식으로 분류한다
  - 주의: 안정형은 "0.25를 넘은 적 없음"으로 정의했으므로 과거 최대가 0.25 미만인 것은 정의상 당연하다. 경보 0.5는 그 두 배로, 과거 어느 달에도 없던 수준이다
- 2022-08 포함률 44.5%(금리 급등기)처럼 과거에도 기준을 크게 벗어난 달이 있었다 → 경보는 실제로 울릴 수 있고, 그때 화면 안내가 필요하다
- **재학습을 드리프트로 앞당기지 않는다**: 데이터가 한 달에 한 번 확정되고(2-1) 재학습이 이미 매달이라, 앞당겨도 새 정보가 없다
- **Evidently는 1차에 쓰지 않는다**: 기본 드리프트 보고서는 Feature마다 판정하는 방식이라 위 측정상 매달 90개 안팎이 걸린다. 묶음별 기준 · 학습 범위 밖 값 · 범위 포함률은 어차피 직접 계산해야 해서, `apt-core`의 순수 함수(테스트 포함)로 만든다. 보고서 형식이 필요해지면 그때 다시 본다
- 결과는 `monitoring_monthly` 테이블(버전 · 지표 · 값 · 기준 · 경보 여부)과 월 보고서(Markdown)로 남긴다. 사용자에게 보여 줄 "모델 성적표"(지난달 실제 오차 · 범위 포함률) 공개 여부는 6장에서 정한다

### 7-4. LLM 변경 관리 — 프롬프트 · 모델 · 도구 · 검색은 모두 Git 버전

| 바뀌는 것 | 버전 | 기록 |
|---|---|---|
| 프롬프트 (시스템 · 리포트 · 상담) | `ai-service/prompts/*.md`, 버전 = 파일 해시 | 모든 추적(7-6)에 `prompt_version` |
| 모델 · effort | 설정 파일 (`claude-haiku-5-5` 같은 고정 ID) | `model`, `effort` |
| 도구 정의 | 3-3 API 스키마 버전 | `tool_schema_version` |
| API · SDK | `anthropic-version` 헤더 · SDK 버전 고정 | `api_version` |
| 검색(정책 문서) | 문서 묶음 해시 + 검색 방식 (7-8) | `index_version` |

- **진실 공급원은 Git**이다. Langfuse 무료 플랜에도 프롬프트 관리 기능이 있지만([가격](https://langfuse.com/pricing)) 쓰지 않는다: 배포가 GitOps(5-6)라 두 곳에서 관리하면 어긋난다. Langfuse에는 버전 이름만 기록해 버전별로 비교한다
- **CI 평가 게이트**: 위 표의 어느 하나라도 바뀌는 PR은 평가 세트를 자동 실행 → 4-5 기준(숫자 정확도 100% · Guardrail 위반 0 · 출처 포함률 등)을 못 넘으면 병합 차단
  - **샘플링 변수(`temperature` 등)를 정할 수 없다**: API 버전 `2026-10-21`에서 제거됨 ([모델 지원 종료 문서](https://platform.claude.com/docs/en/about-claude/model-deprecations)의 파라미터 표) → 같은 질문도 답이 달라질 수 있어 **같은 세트를 3회 실행하고, 3회 모두 기준을 통과**해야 한다
  - 비용: PR 게이트는 20문항 × 3회(Haiku 5.5 약 $0.06, 4-5 단가), 전체 100문항 × 3회는 확정할 때만 (Haiku 약 $0.36 · Sonnet 약 $6.9) → 개발 · 평가 예산(4-5, 서비스 예산과 별도)
- **Claude 모델 교체 절차**: Anthropic은 공개 모델 지원 종료 **최소 60일 전**에 메일 · 문서로 알린다. 현재 후보는 `claude-haiku-5-5` 2027-10-07, `claude-sonnet-5-5` 2027-09-28 **이전에는 종료되지 않음**(같은 문서, 2026-11-18 조회)
  - 알림 또는 새 모델 출시 → 전체 평가 × 3회로 기존 모델과 같은 기준 비교 → 통과하면 설정 PR → CI 게이트 → 배포. ML의 설정 변경(7-1)과 같은 원칙
  - 사용 중인 모델 확인: 콘솔 사용량 내보내기(키 · 모델별)로 지원 종료 모델 사용이 남았는지 본다 (같은 문서)

### 7-5. 실시간 Guardrail (답변을 보여 주기 전에)

| 검사 | 방법 | 걸리면 |
|---|---|---|
| **숫자 검사** | 답변 속 금액 · 비율 · 날짜를 뽑아 이번 대화의 도구 결과(3-3 API 응답)에 있는지 코드로 대조 — 4-5 평가 기준과 같은 함수 | 답변 대신 ML 카드(적정가 · 범위 · 판정 · 근거 거래)만 보여 주고 "설명을 만들지 못했습니다" (12장 장애 대응과 같은 화면) |
| 금지 표현 | "감정가" · 매수/매도 권유 · 미래 가격 단정 (기획서 법적 위험, 감정평가법 확인 결과) | 같은 처리 + 기록 |
| 개인정보 | 사용자 입력에서 전화번호 · 주민등록번호 · 이메일 형식을 가린 뒤 Claude · Langfuse로 보냄 | 가린 값만 전송 |
| 입력 | 길이 상한, 세션 턴 상한 (4-4) | 안내 문구 |

- **1차는 답변을 끝까지 받은 뒤 검사하고 보여 준다(스트리밍 안 함)**: 검사 전에 화면에 나간 숫자는 되돌릴 수 없다. 대신 기다리는 시간이 늘어난다 → ④에서 응답 시간을 재고, 너무 길면 문장 단위로 검사하며 보여 주는 방식을 검토한다
- 이 검사들은 LLM을 부르지 않아 비용이 없고, 모든 답변(100%)에 적용한다

### 7-6. 운영 추적 · 평가 (Langfuse Cloud Hobby)

- 무료 플랜: 월 5만 단위(단위 = 추적 · 관측(span · generation) · 점수 하나), 보관 30일, 사용자 2명. 데이터셋 · 실험 · LLM 채점 · 주석 큐 1개 · 사용자 피드백 포함 ([가격](https://langfuse.com/pricing), 2026-11-18 조회)
- 사용량 추정: 상담 1회 = 추적 1 + generation 2 + 도구 span 약 2 + 점수 약 1 ≈ **6단위**(추정) → Haiku 하루 상한 약 160회(4-4)를 매일 다 써도 월 약 2.9만 단위로 한도 안. ④에서 실제 단위 수를 재 확정
- **매 답변 (100%, 비용 0)**: 7-5 검사 결과 · 토큰 · 비용 · 지연 · 도구 호출 · 실패를 점수 · 메타데이터로 기록
- **표본 채점 (매일, `llm-eval-daily` CronJob)**: 전날 추적 중 일부를 Langfuse API로 가져와 LLM 채점(출처 포함 · 한국어 자연스러움 · 질문에 답했는가) → 점수를 Langfuse에 다시 기록
  - Langfuse 화면의 자동 채점 기능을 쓰지 않고 우리 CronJob으로 돌리는 이유: Langfuse가 직접 LLM을 부르면 그 비용이 **4-4 하루 비용 상한 계산을 거치지 않는다**. 우리 Job은 같은 비용 계산기를 거치고, 상한에 가까우면 채점을 건너뛴다
  - 표본 비율 · 채점 기준은 평가 세트를 만들 때(④) 정한다
- **보관 30일 → 우리 DB로 요약**: `llm-eval-daily`가 하루 요약(상담 수 · 비용 · 지연 p50/p95 · 실패율 · Guardrail 차단 수 · 피드백 · 채점 평균, 버전별)을 `llm_daily` 테이블에 쓴다 → 30일이 지나도 프롬프트 · 모델 버전별 추이를 볼 수 있다 (포트폴리오 "버전별 환각률 변화"의 원천)
- 경보: Guardrail 차단률 · 실패율은 ④ 측정 후 기준을 정하고, 비용은 4-4 · 5-7 그대로

### 7-7. 피드백 루프

1. 답변마다 좋아요/싫어요 · 오류 신고 → Postgres + Langfuse 점수 (1차는 로그인이 없어 세션 단위)
2. 주 1회 싫어요 · 신고 · Guardrail 차단 건을 Langfuse 주석 큐(무료 1개)에서 사람이 검토 (Django Admin은 2차)
3. 정답을 사람이 달아 **평가 세트 후보**로 추가 → 평가 세트 파일(Git)에 PR → 이후 모든 CI 게이트에 포함
- ML 쪽 피드백은 이미 있다: 새로 확정된 실거래가 정답이다 (OOF, 2-5 · 7-3)
- 보관 기간은 6-6 ④ (결정 2026-11-20): 대화 원문은 Langfuse 30일, 우리 DB에는 원문 없이 요약 · 점수만. 호가는 판정 이벤트로 12개월

### 7-8. 정책 질문의 검색 방식 — ④에서 평가로 정한다

- 지금 계획은 Qdrant 벡터 검색(정책 RAG)이지만, 정책 이벤트는 **196건**(2-2)뿐이고 이미 날짜 · 대상 · 출처 URL이 있는 구조화 표다
- 후보: (가) `policy_event` 표를 날짜 · 지역 · 종류로 조회하는 도구 (나) 보도자료 원문 벡터 검색 — 임베딩 모델을 따로 정해야 하고(Claude API에는 임베딩 모델이 없음), Qdrant · 임베딩 비용 · 메모리가 든다
- 평가 세트의 정책 질문으로 두 방식을 같은 기준(출처 정확도 · 답변 정확도, 검색 정답 세트의 recall@5)으로 비교해 **(가)로 충분하면 Qdrant를 빼고**, 부족할 때만 (나)를 들인다. 기준은 평가 세트를 만들 때 결과 전에 고정
- 어느 쪽이든 문서 묶음이 바뀌면(정책 PR 병합) `index_version`이 바뀌고 7-4 CI 게이트를 다시 돈다
